# МТС Exolve — Number Lookup (HLR) API

Что проверено по документации Exolve на 06.10.2026. Базовый адрес — `https://api.exolve.ru/`,
авторизация — `Authorization: Bearer <API-ключ приложения>`, тело запроса у всех методов одно:

```json
{ "number": "7XXXXXXXXXX" }
```

Номер — одиннадцать цифр, начиная с `7`, **без `+`**. Формат с плюсом отклоняется как
`incorrect number format`, и запрос при этом тарифицируется.

## Тарификация

**Платный запрос — любой запрос.** Если по номеру нет данных (обычно — не было активности около
двух лет), API возвращает ошибку и всё равно списывает деньги. Это не исключительный случай, а
документированное поведение, и из него следует, что HLR нельзя перепродавать «за успешную
проверку»: успеха у него нет как категории.

## Методы по одному номеру

### `POST hlr/v1|v2/GetActivityScore`

Оценка активности номера в сети.

| Поле ответа | Тип | Значение |
| --- | --- | --- |
| `number` | uint64 | номер запроса |
| `result` | string | оценка от `"0"` до `"1"`: 0 — самая низкая, 1 — самая высокая |
| `owner_id` | string | идентификатор оператора |
| `region_code` | uint32 | код региона покупки SIM |

Единственный метод с документированной `v2`. Ограничения по оператору в документации **нет** —
заявлено «по номерам любых операторов РФ».

### `POST hlr/v1/GetSimStatus`

| Поле ответа | Тип | Значение |
| --- | --- | --- |
| `number` | uint64 | номер запроса |
| `is_registered` | bool | `true`, если SIM регистрировалась в сети за последние 24 часа |

**Только номера МТС:** «Получить данные можно только по номерам оператора МТС». По чужому
номеру — `400 enter another number`.

### `POST hlr/v1/GetBaseNumberInfo`

| Поле ответа | Тип | Значение |
| --- | --- | --- |
| `number` | uint64 | номер запроса |
| `owner_id` | string | идентификатор оператора |
| `region_code` | uint32 | код региона покупки SIM |
| `network_code` | string | **на деле** буквы страны + MCC + MNC, например `RU25002` |
| `mnp` | bool | номер переносился между операторами |

Ограничение по оператору не упомянуто, и на практике метод действительно отвечает по не-МТС
номеру. Для России MCC — `250`; MNC: МТС `01`, МегаФон `02`, Tele2 `20`, Билайн `99`.

**`network_code` описан в документации неверно.** Там сказано «три цифры кода страны (MCC) плюс
две цифры кода оператора (MNC)», то есть пять цифр. Реально приходит `RU25002` — сначала буквенный
код страны. Разбор по позициям из документации даёт `RU2` и `50`, то есть неправильного оператора;
SDK отбрасывает буквы и берёт цифры.

Ещё наблюдение с живого API: `owner_id` приходит как `mMEGAFON` — с лишней буквой впереди, так что
сравнивать его на точное равенство нельзя, только на вхождение.

**Почему это единственный надёжный способ узнать оператора.** Префиксная таблица врёт на
перенесённых номерах: при `mnp = true` «мтс-овский» префикс принадлежит другому оператору. Для
решений вроде «пускать ли этот номер в метод, который работает только на МТС» нужен этот метод,
а не справочник префиксов.

### `POST hlr/v1/GetLastDateActivity`

| Поле ответа | Тип | Значение |
| --- | --- | --- |
| `number` | uint64 | номер запроса |
| `days_since_last_activity` | **string** | число дней строкой, например `"2"` |

### `POST hlr/v1/GetBestCallTime` и `POST hlr/v1/GetBestSmsTime`

| Поле ответа | Тип | Значение |
| --- | --- | --- |
| `number` | uint64 | номер запроса |
| `result` | string | интервал в UTC+0, например `"17:00:00,21:00:00"` |

**Только номера МТС** — в документации с оговоркой «пока».

## Пакетные методы — до 50 000 номеров

### `POST hlr/v1/GenerateActivityScoreReport` и `POST hlr/v1/GenerateBestCallTimeReport`

| Поле запроса | Тип | Значение |
| --- | --- | --- |
| `numbers` | string | список номеров **файлом в base64**, номер в формате `7XXXXXXXXXX` |

| Поле ответа | Тип | Значение |
| --- | --- | --- |
| `file_uuid` | string | идентификатор отчёта для `GetHLRReport` |

Не массив JSON, а именно файл в base64 — внутренний формат файла документация не описывает. SDK
разделяет номера переводом строки; если выяснится, что Exolve ждёт другое, есть перегрузка
`GenerateReportAsync`, принимающая готовый base64.

Ошибки: `400 at least one number is required`, `400 invalid …Numbers: value length must be at
least 1 bytes`. По отчёту активности заявлены номера **любых операторов РФ**.

### `POST hlr/v1/GetHLRReport`

Запрос — `file_uuid`.

| Поле ответа | Тип | Значение |
| --- | --- | --- |
| `file_uuid` | string | идентификатор отчёта |
| `created_at` | timestamp | **срок хранения** — 30 дней с создания, а не время создания |
| `type` | enum | 1 — activity_score, 2 — best_call_time |
| `status` | enum | см. ниже |
| `number_total` | int32 | сколько номеров в отчёте |
| `base64` | string | результаты проверки |

| Статус | Значение |
| --- | --- |
| 1 | ожидает проверки |
| 2 | проверка идёт |
| 3 | отчёт готов |
| 4 | готов, но есть ошибки |
| 5 | срок хранения истёк |

**Название `created_at` обманчивое** — по документации это дедлайн хранения. В SDK поле
называется `RetainedUntil`.

### `POST hlr/v1/GetHLRListReport`

| Поле запроса | Тип | Обяз. |
| --- | --- | --- |
| `date_from` | timestamp (RFC-3339) | да |
| `date_to` | timestamp (RFC-3339) | да |
| `limit` | uint64 | нет |
| `offset` | uint64 | нет, с нуля |

Ответ — `reports`: массив объектов той же формы, что у `GetHLRReport`.

Ошибки: `invalid …DateFrom: value is required`, `invalid …DateTo: value is required`,
`date_from later than date_to`.

**Расхождение в типах.** У `GetHLRReport` поле `status` документировано числом, у
`GetHLRListReport` — строкой, при одинаковых значениях 1…5. SDK разбирает оба варианта, а
неизвестное значение превращает в `Unknown`, а не в исключение: новый статус у поставщика не
повод уронить разбор отчёта.

## Форма ошибки — не та, что в документации

Проверено на `api.exolve.ru` 07.10.2026: ошибка приходит **вложенным объектом**, а не строкой.

```json
{"error":{"message":"hlr is disabled on the application"}}
```

В документации встречается плоская форма `{"error":"…"}`. Модель только под неё означает, что
текст ошибки всегда пустой, а признаки вроде «номер не МТС» молча не срабатывают — именно так и
было в первой версии SDK. Разбираются обе формы, а сырое тело сохраняется в
`ExolveApiException.RawBody`, чтобы незнакомая форма оставалась видимой, а не превращалась в
пустую строку.

## Услугу надо включить на приложении

Пока HLR не включён, **все** методы отвечают `400 hlr is disabled on the application` — независимо
от номера и оператора. В SDK это `ExolveApiException.IsHlrDisabled`.

Как включить, документация не объясняет: ни на странице раздела, ни в описаниях методов нет
условий подключения. Остаётся личный кабинет или обращение к менеджеру Exolve.

## Ошибки

| Код | Текст | Что это |
| --- | --- | --- |
| 400 | `incorrect number format` | формат номера или отсутствует обязательный параметр |
| 400 | `enter another number` | номер не МТС, а метод работает только по МТС |
| 400 | `hlr is disabled on the application` | услуга не включена в настройках приложения |
| 400 | `customer has not signed, the number must match your confirmed phone number` | тестовый период: только свой подтверждённый номер |
| 401 | `incorrect authorization token` | неверный API-ключ |
| 403 | — | нет доступа с этим ключом |
| 404 | `404 page not found` | неверный URL |

Последнюю 400-ю легко спутать с ограничением по оператору — в SDK они разведены
(`IsUnsignedCustomer` против `IsNonMtsNumber`).

## Что надо уточнить у Exolve письменно

Exolve сказал нам словами, что PC/FC и HLR работают **только по номерам МТС**, но документация
по методам противоречива: у `GetSimStatus`, `GetBestCallTime` и `GetBestSmsTime` ограничение
прописано, у `GetActivityScore` прямо заявлено обратное, у `GetBaseNumberInfo` не сказано ничего.
Разница решает, можно ли продавать HLR как проверку любого номера или только мтс-овского.
